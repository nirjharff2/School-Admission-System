# Assumptions

Decisions the specification left open, each with its reasoning. The first part is the short version; the sections after it give the reasons.

## Decisions at a glance

| Topic | Decision |
|---|---|
| **IDs** | `c_` / `h_` + 16 random lower-case hex characters, generated in the application (opaque, non-sequential). |
| **Student identity** | `X-Student-Id` must be exactly 17 ASCII digits; checked before anything else (a bad header is a `400` even for an unknown class). The UI saves it in `localStorage` and flags anything else. |
| **Expiry** | `expiresAt = createdAt + HOLD_DURATION_SECONDS` (default 600). A `HELD` hold past `expiresAt` is reported `EXPIRED` by every read and is not counted as a seat, whether or not the background sweeper has stored the change yet. The sweeper (every `EXPIRY_SWEEP_INTERVAL_SECONDS`, default 2) makes the stored rows agree. |
| **Concurrency** | Applying locks the class row (`SELECT … FOR UPDATE`) in one PostgreSQL transaction, then counts and inserts; confirm and cancel are single conditional `UPDATE`s; a partial unique index allows one active hold per student per class. It holds for any number of backend processes. |
| **Confirm** | Owner only, and only while `HELD` and unexpired; repeating it on a `CONFIRMED` hold is `200` and changes nothing. |
| **Cancel** | `HELD` → `204` and the seat is free at once; repeat on `CANCELLED` → `204`; `CONFIRMED` → `409 hold_confirmed` (a paid seat is not released through this API, there is no refund flow); expired → `409 hold_expired`. |
| **Duplicate / full** | The duplicate check runs first, so a student who already holds the last seat gets `already_applied`, not `no_seats_available`. A student may apply again after a cancellation or an expiry. |
| **Other student's hold** | `403 not_your_hold` (hold ids are unguessable and `GET /holds/{id}` already shows existence). |
| **Errors** | Every error body is `{ "error": "<code>", "message": "<sentence for a person>" }`, including framework errors. |
| **CORS** | Any origin, header and method: identity is a plain header, there are no cookies or credentials. |
| **Polling** | Class list every 4 s; application and My Applications every 15 s (and right after an expiry, and when the tab regains focus); the countdown runs locally every second. |
| **Docker** | Fixed compose project name, Postgres not published on the host, backend on 8080 (and an identical second backend on 8081 sharing the database), frontend on 3000, healthcheck-ordered start. |

Error codes by status:

| Status | Codes |
|---|---|
| `400` | `validation_failed`, `invalid_request`, `student_id_required`, `invalid_student_id` |
| `403` | `not_your_hold` |
| `404` | `class_not_found`, `hold_not_found`, `not_found` |
| `405` | `method_not_allowed` |
| `409` | `already_applied`, `no_seats_available`, `hold_expired`, `hold_cancelled`, `hold_confirmed`, `hold_state_changed` |
| `503` | `service_busy` (database overloaded or deadlock victim; `Retry-After: 2`) |
| `500` | `internal_error` |

## Identifiers

- Class ids are `c_` + 16 lower-case hex characters (64 random bits from a cryptographic RNG), e.g. `c_3f9a1b7c5d2e4a68`. Hold ids use the prefix `h_`.
- Reason: opaque, non-guessable, no count leak, short enough to read out, and generated in the application so no database round trip or sequence is needed. The primary key guarantees uniqueness; a collision (about 1 in 10^19 per pair) would surface as a 500, not as silent corruption.

## Error responses

- Every error is JSON `{ "error": "<machine_code>", "message": "<human sentence>" }`, including framework-produced ones (malformed JSON, unknown route `404 not_found`, wrong method `405 method_not_allowed`, unhandled exception `500 internal_error`), so the UI parses one shape. Messages never contain stack traces or internals.
- `POST /classes`: `400 validation_failed` when `name` is missing, blank after trimming, longer than 200 characters or contains control characters, or `totalSeats` is missing or below 1; `400 invalid_request` when the body is not valid JSON or a field has the wrong type (`"totalSeats": "many"`, `2.5`). Names are stored trimmed.
- `GET /classes/{id}`: `404 class_not_found`.
- Student identity (`X-Student-Id`, required on apply, confirm, cancel and `/me/holds`): `400 student_id_required` when absent or blank, `400 invalid_student_id` when it is not exactly 17 ASCII digits (full-width and other-script digits are rejected). It is checked first, so a bad header is a `400` even for an unknown class or hold.
- `POST /classes/{id}/holds`: `404 class_not_found`; `409 already_applied` when the student already has an active hold in that class; `409 no_seats_available` when the class is full. The duplicate check runs first.
- `GET /holds/{id}`: `404 hold_not_found`; no header needed; it returns exactly the contract fields (no `studentId`), so a hold id does not reveal whose application it is.
- `GET /me/holds`: newest first; `[]` when the student has none.
- Confirm and cancel: unknown hold `404 hold_not_found`; another student's hold `403 not_your_hold` and the hold is left untouched (not a 404: ids are unguessable and `GET /holds/{id}` already reveals existence, so hiding it adds nothing and the 403 gives a clear message).
  - **Confirm**: `HELD` and unexpired → `200 { holdId, status: "CONFIRMED" }`; already `CONFIRMED` → `200` again, nothing changes (idempotent); expired (stored `EXPIRED`, or `HELD` past `expiresAt`) → `409 hold_expired`; `CANCELLED` → `409 hold_cancelled`. An expired hold is never revived; the guardian applies again.
  - **Cancel policy**: `HELD` and unexpired → `204`, status `CANCELLED`, the seat is free at once and the student may apply again; already `CANCELLED` → `204` (the requested end state already holds); `CONFIRMED` → `409 hold_confirmed` (once the fee is paid the application cannot be withdrawn here: there is no refund flow and silently freeing a paid seat would be wrong); expired → `409 hold_expired` and the status stays `EXPIRED`.
  - `409 hold_state_changed` exists only for a race where the hold changes between the conditional update and the follow-up read in a way the update should have caught; the client can retry.

## Configuration

- Database: the standard ASP.NET Core key `ConnectionStrings__Default` (Npgsql connection string). The app refuses to start without it. `appsettings.Development.json` points at `localhost:5432` for `dotnet run` outside Docker.
- Schema: EF Core migrations run automatically at start-up, so a fresh database needs no manual step.
- CORS allows any origin, header and method. There are no cookies or credentials (identity is a plain header), so a wildcard origin adds no risk and works for whatever host and port serve the frontend.
- Time comes from an injected `TimeProvider` (UTC); timestamps are stored as `timestamptz`.
- The API binds `http://0.0.0.0:8080` only when no address is configured; `--urls`, `ASPNETCORE_URLS` or `ASPNETCORE_HTTP_PORTS` take precedence (a second instance on another port: `ASPNETCORE_URLS=http://0.0.0.0:8081`).

## Hold expiry

- `HOLD_DURATION_SECONDS`: whole seconds, at least 1, default 600; an invalid value stops the app at start-up instead of failing on the first request.
- `createdAt` is the request time truncated to whole seconds and `expiresAt = createdAt + HOLD_DURATION_SECONDS` exactly, serialized as `2026-11-01T04:10:00Z` (UTC, whole seconds, trailing `Z`) as in the contract example. A hold lives up to one second less than the wall-clock time since the request.
- A hold is expired when `now >= expiresAt`. Every read computes the status: a stored `HELD` row past its `expiresAt` is reported `EXPIRED` and does not count as held or occupy a seat, whether or not the sweeper has rewritten the row yet. A seat is therefore free at `expiresAt` itself, not at the next sweep.
- Only `CONFIRMED` and unexpired `HELD` holds are active: they occupy a seat and block a second application by the same student to the same class. After an expiry or a cancellation the student can apply again.
- Sweeper: a background service in every backend instance stores lapsed `HELD` rows as `EXPIRED` at start-up and then every `EXPIRY_SWEEP_INTERVAL_SECONDS` (whole seconds, at least 1, default 2), so the database itself is right without any API call and direct queries agree with the API. A failed sweep (database briefly unreachable) is logged and retried on the next tick and never stops the API.

## Concurrency strategy

- **Capacity (`heldSeats + confirmedSeats <= totalSeats`) is enforced inside PostgreSQL with a pessimistic row lock on the class row.** Applying runs one transaction: `SELECT total_seats FROM classes WHERE id = ? FOR UPDATE`; then, holding the lock, read the clock, store the class's lapsed `HELD` holds as `EXPIRED`, check for an active hold by the same student (`409 already_applied`), count the active holds (`CONFIRMED`, or `HELD` and unexpired), refuse with `409 no_seats_available` when the count has reached `totalSeats`, otherwise insert and commit.
  - Why it holds for any number of threads or backend processes: the lock lives in the database. Applications for one class queue on the row lock; under READ COMMITTED each statement after the lock sees everything the previous lock holder committed, so every count includes every seat already granted. Applications for different classes do not block each other. A second backend instance on the same database is covered by exactly the same mechanism.
  - Nothing else can add to the occupied count: the only `INSERT` into `holds` is that transaction. The other writers only move a row out of the active set (cancel: `HELD` → `CANCELLED`; expiry: `HELD` → `EXPIRED`) or turn one active row into another (confirm: `HELD` → `CONFIRMED`), so none of them can overbook and none needs the class lock.
  - Backstop: the partial unique index `ux_holds_active_student_class` on `holds (class_id, student_id) WHERE status IN ('HELD','CONFIRMED')` enforces one active application per student per class even if some code path skipped the lock; a violation is answered with the same `409 already_applied`. The index does not know about time, so the transaction first stores the class's lapsed rows (including the student's own) as `EXPIRED`. A partial index on `expires_at WHERE status = 'HELD'` serves the sweeper.
  - The migration that adds the unique index first repairs old rows so start-up cannot fail on an existing database: lapsed `HELD` rows become `EXPIRED`, and where a student has several active holds in one class it keeps a `CONFIRMED` one (money was paid) or else the newest and cancels the rest. A test covers it.
- **Confirm** is one conditional `UPDATE … WHERE id = ? AND student_id = ? AND status = 'HELD' AND expires_at > now`; **cancel** is the same shape. Neither takes the class lock, so they are never queued behind a burst of applications. The row can leave `HELD` only once, so repeated or simultaneous confirms count a seat once (a test fires 20 parallel confirms). A hold that expires at the very moment its owner confirms is settled by row locks: an application first marks the class's lapsed rows `EXPIRED` with an `UPDATE`, which must take each row's lock, so either the confirm wins the row (the application then counts the seat) or the application wins it (the confirm matches nothing and answers 409). A test pins this deterministically.
- **Expiry statements lock rows in id order.** The sweeper (all classes) and an application's own-class expiry both update many rows; a plain `UPDATE … WHERE` locks them in plan order, so two such statements over overlapping rows can deadlock (PostgreSQL `40P01`), which was reproduced under churn. Both now `SELECT id … ORDER BY id FOR UPDATE` first and then update (`HoldExpiry`), so they cannot wait on each other in a cycle, and `FOR UPDATE` re-checks the predicate so a row a confirm just turned `CONFIRMED` is skipped. `40P01` is also treated as a retryable overload (`503 service_busy`) as a safety net. A test runs sweeps against applications over shuffled lapsed holds for 80 rounds.
- **Overload handling.** Every application waiting on the class lock holds a pooled connection, and one class grants roughly 40-100 applications per second, so a burst of thousands could exhaust the pool. The app therefore (1) bounds the connection pool (`Maximum Pool Size=30` unless the connection string sets its own, so three instances fit PostgreSQL's default 100 connections); (2) puts a gate in front of the database work, admitting at most 3 applications per class (64 hashed gates) and 15 per process at once while the rest wait in memory, so a burst on one class does not hold up confirms, page loads or other classes; (3) answers futile applications (unknown class, duplicate, class already full) with one plain read before taking the lock (it can never grant a seat; every grant goes through the locked path, which repeats all checks); (4) reads the clock only after the lock is held, so a request that queued for seconds does not stamp a stale `createdAt` or judge expiry with an old "now"; (5) answers `503 service_busy` with `Retry-After: 2` (not a 500) when the database still cannot serve a request in time (pool or command timeout, no free connection, deadlock victim), and drops a disconnected client silently. The gate is a throughput guard only; correctness comes from the database lock. Limit: classes share the 64 gates by hash and the 15 process slots, so with five or more classes busy at once a further class can queue briefly.
- **Measured** (development machine, two backend processes on one PostgreSQL, bursts sent as simultaneous requests, plus a few probe requests sent during the burst): 3000 requests for 300 seats gave 299 `201` + 2701 `409` in about 12 s; 2500 for 2000 seats gave 1999 + 501 in about 44 s (about 46 grants per second, serialized by the class lock); during bursts a confirm answered in 9-69 ms and an application to an idle class in about 30 ms; no 5xx, both processes reported identical counts, and no class was ever above its capacity. A burst that grants thousands of seats in one class therefore takes about a minute, but the seat counts stay exact.
- **Clocks.** Expiry decisions compare `expires_at` with the application's clock, not the database's; all backend instances are assumed to have clocks that agree to well under a second (same host, or NTP-synced hosts as in `docker compose`).
- **Start-up.** Every instance applies pending migrations under a PostgreSQL advisory lock (`pg_advisory_lock`) taken on its own non-pooled connection to the always-present `postgres` database (advisory locks are per database and the application's database may not exist yet; if that database is unreachable with the given credentials the application's own database is used). EF Core 8 does not lock migrations itself, and two backend processes starting together on an empty database raced on creating `__EFMigrationsHistory` and one crashed; with the lock the second waits and applies nothing. Tests start four instances at once and one against a server where the database does not exist.

## Several backend instances

The brief's optional requirement: two backend processes on different ports sharing one database must still never exceed `totalSeats`. This holds without any extra mechanism, because nothing the guarantee relies on lives in a process:

- **Capacity** is decided under the class-row lock, which is a PostgreSQL lock, so applications arriving at either process for the same class queue on the same lock and each count includes every seat the other process has already granted. The only `INSERT` into `holds` is that transaction, so no code path in either process can add a seat without passing it. The per-process gate described above only limits how many requests wait at once; it is not part of the guarantee, so having one gate per process changes nothing.
- **One active application per student** is enforced by the partial unique index in the database, so a student cannot hold two seats in a class by applying through both ports.
- **Confirm and cancel** are single conditional `UPDATE`s on the hold row, so a confirm through one process and a cancel or expiry through the other have exactly one winner (the row can leave `HELD` only once).
- **The expiry sweeper is safe to run in every instance.** Each sweeper runs the same idempotent statement (it locks the lapsed `HELD` rows in id order and sets them to `EXPIRED`); a row can leave `HELD` only once, so two sweeps over the same rows simply find them already done; there is no leader election to get wrong. Both sweepers use the id-ordered locking that also protects them from deadlocking with applications (see above), and the sweepers of the two instances cannot deadlock with each other for the same reason.
- **Start-up** is serialized by the advisory lock, so two instances starting together on an empty database both come up.
- **Reads agree.** Every read computes the status from `expiresAt` and the same stored rows, so both processes report identical counts at any moment (subject to the clock assumption above).

Evidence: an in-process test sends 200 applications for 10 seats split over two hosts on one database (exactly 10 `201`); another test runs applications, confirms and the two instances' sweepers (1-second holds) for 7 seconds over two hosts and checks that no response is a 5xx, that held + confirmed never exceeds the seats at any observation on either instance, and that both instances end with identical counts; and the compose stack was exercised with 200 requests for 9 seats and 1500 requests for 40 seats alternating between ports 8080 and 8081: exactly 9 and exactly 40 `201`, the rest `409`, no 5xx, `heldSeats` equal to the seats on both ports. Earlier manual runs used two real operating-system processes with bursts of up to 4000 requests (see *Measured*).

## Frontend: shell and student identity

- Routing is hash based (`#/classes`, `#/classes/new`, `#/application`, `#/application/{holdId}`, `#/my-applications`), with no routing library and no server rewrite rules, so a refresh or a pasted link stays on the same screen behind any static file server. The "Application" entry opens a small form that takes the hold id the backend returned; the other screens link to an application directly.
- The student id box saves what is typed (trimmed) to `localStorage` key `admission.studentId`, valid or not, so a half-typed number survives a refresh. Valid means `^[0-9]{17}$` (ASCII digits only, the same rule as the backend). Other tabs follow changes through the `storage` event; if storage is blocked the box still works in memory.
- The box does not scold a number that is still being typed ("4 of 17 digits so far"); it flags the text when it cannot become valid (a non-digit, more than 17 characters), after the box is left, or at once for an invalid id saved earlier.
- An invalid id blocks student actions twice: screens that need it show a message instead of their content, and the API client refuses to send any student-scoped call with an invalid id (it fails locally with code `invalid_student_id`).
- The API client turns every failure into `ApiError { code, message, status }`: the backend's `error` and `message` when present, else `network_error`, `timeout`, `server_error` / `request_failed` (non-JSON error body, with a generic sentence by status) or `invalid_response`.
- `VITE_API_BASE_URL` is read when the frontend is built (Vite inlines it); unset or blank means `http://localhost:8080`; trailing slashes are removed.

## Frontend: classes and applications

- **Create Class** checks the backend's rules before sending (name trimmed, 1-200 characters, no control characters; seats a whole number from 1 to 2,147,483,647, the backend's 32-bit limit) and shows each message under its field; the backend's own `400` message is still shown if it rejects something the browser accepted. After success the form is cleared and stays (an admin often adds several classes) with a link to the list; after a failure the typed values are kept.
- **Class List**: Apply is disabled while the student id is invalid, while the class shows 0 available seats ("Full"), and while another Apply is in flight (no double submit); the tooltip says why. Seat counts on screen can be stale, so the server decides: its `409 no_seats_available` / `409 already_applied` messages are shown above the table and the list is refetched. Success goes to `#/application/{holdId}`. Button label: "Apply (আবেদন করুন)".
- **Application** (`#/application/{holdId}`): shows `GET /holds/{id}` (no header needed) plus the class name from `GET /classes/{id}` (loaded once; if it fails a notice is shown, the class id is displayed and loading is retried). Pay ("Pay admission fee (ভর্তি ফি দিন)") and Cancel ("Cancel (বাতিল)") are enabled only while the status shown is `HELD` and the student id is valid, and only one action runs at a time; Cancel asks once more inline because it releases the seat. The new status from the response is shown at once and then confirmed by a refetch; a refused action shows the backend's message and refetches. The expiry time is shown only for `HELD` and `EXPIRED` applications.
- **My Applications**: keyed by the student id, so changing the id shows that student's list; newest first as the backend returns it; an invalid id shows the "enter a valid ID" message and fetches nothing.

## Frontend: polling and live expiry

- **Class list: every 4 seconds** (`GET /classes`); a seat taken or released elsewhere shows within about 4 s (measured 4.0-4.1 s), which is "every few seconds" without a reload. Polling rather than SSE/WebSocket keeps the backend a plain request/response API, and 4 s of staleness is harmless because the server decides who gets a seat.
- **Application and My Applications: every 15 seconds while something is `HELD`, plus right after a hold's `expiresAt` and whenever the tab or window regains focus.** A `CONFIRMED`, `EXPIRED` or `CANCELLED` application can no longer change, so the detail screen stops its timer for those; My Applications keeps its 15 s timer because another device can add an application.
- Polling never runs two requests at once, never runs in a hidden tab (it refetches at once when the tab is shown again), and a failed refetch keeps the last data on screen with a "could not be refreshed" notice.
- **Countdown:** the Application screen counts down to `expiresAt` locally every second from the browser clock (no requests), flips to `EXPIRED` and disables Pay and Cancel the moment the clock reaches `expiresAt` without a reload, and refetches 0.5 s later to confirm. My Applications flips lapsed rows the same way.
- **Clock skew:** the server stays the authority. If the browser clock is ahead, the screen shows `EXPIRED` for about half a second, then the confirming refetch (sent after `expiresAt`) still says `HELD`, so the screen shows `HELD` at `0:00` with "Confirming with the server…", keeps Pay enabled and refetches every 2 s until the server says `EXPIRED` (tested with a browser clock 10 s ahead). If the browser clock is behind, the countdown ends late and Pay may be pressed after the real expiry; the server answers `409 hold_expired` and the screen then shows `EXPIRED`. The API sends no server time, so the skew cannot be measured directly.

## Frontend: error messages

- Every failure is shown as text on the screen where it happened, through one component (`ErrorBanner`: a bold "what failed" sentence, then the reason, with "Try again" or "Dismiss" where they make sense), announced to screen readers (`role="alert"`). Nothing is console-only.
- The reason is the backend's own `message` whenever the answer has one (409, 400, 403, 404, 503); the backend wrote those for a guardian to read. When it has none (a proxy page, an unexpected status) the client uses its own sentence for that status; a failed connection says "Cannot reach the server. Check your connection and that the backend is running, then try again."
- Requests time out after 15 seconds ("The server took too long to answer. Please try again in a moment."), so a hung server cannot leave a button spinning or stop polling for ever. A refusal that asking again cannot change (4xx other than 408/429) is not retried on a timer.
- Errors that React error boundaries cannot see (a rejected promise nobody caught, an exception in an event handler) are caught by `window` handlers and shown as a dismissible banner with a generic sentence (an `ApiError` keeps its own readable message); the banner clears when the user moves to another screen. A crash while rendering a screen is caught by a per-screen error boundary that keeps the id box and navigation usable; navigating elsewhere retries.

## Docker and compose

- Services: `postgres` (16-alpine, named volume `pgdata`), `backend` (multi-stage .NET 8 SDK to ASP.NET runtime image, port 8080, runs as the image's non-root user, applies migrations at start-up), `frontend` (Node 22 build, then the static files served by nginx on container port 80, published on host port 3000). Every setting has a default; a `.env` file is optional.
- The compose project has a fixed name (`name: school-admission`), so the data volume is `school-admission_pgdata` whatever the folder is called and cannot collide with another project's volume.
- `backend2` is a second container of the same image on the same database (host port 8081, `BACKEND2_PORT`), declared with a shared YAML anchor so both services have identical settings; it is built once (`image: school-admission-backend`). Both wait for the database, and both start at the same moment on an empty volume, which the migration lock (see *Several backend instances* above) makes safe. The frontend uses `backend` only. Two instances use at most 2 × 30 database connections, within PostgreSQL's default of 100.
- PostgreSQL is not published on the host: the backend reaches it by service name. Publishing 5432 would fail on any machine that already runs a PostgreSQL there, and nothing outside the stack needs the database (`docker compose exec postgres psql -U admission admission` gives a shell).
- Start order uses healthchecks and `depends_on: condition: service_healthy` (backend waits for the database, frontend for the backend), so `docker compose up --wait` returns only when everything answers. The database check is `pg_isready -h 127.0.0.1` (over TCP: while a new volume initialises, PostgreSQL's temporary server listens only on the unix socket). The backend check is a `GET /classes` that must return 200, sent with bash's `/dev/tcp` because the runtime image has neither curl nor wget; the frontend's is a `wget` of the start page. The backend does not retry a failed first connection itself: it exits and `restart: unless-stopped` brings it back.
- `VITE_API_BASE_URL` is the address the browser uses for the API, not an address between containers, so its default is `http://localhost:8080` (it follows `BACKEND_PORT`); Vite bakes it into the JavaScript at build time, so changing it needs `docker compose up --build`. The backend allows any origin, so the page on port 3000 may call the API on port 8080.
- Host ports are `${BACKEND_PORT:-8080}:8080` and `${FRONTEND_PORT:-3000}:80`: the defaults are the contract; the variables exist for machines where a port is taken. Hash routing means nginx needs no rewrite rules.
- `backend` and `frontend` use `restart: unless-stopped`; the data survives in the named volume and only `docker compose down -v` deletes it. The frontend container is stock `nginx:1.27-alpine` (its master process runs as root, as in the official image; it only serves static files and holds no secrets); an unprivileged nginx image would need another container port and is not worth the extra moving part.

## Repository and tooling

- The solution uses the classic `.sln` format (not `.slnx`) so it builds with both the .NET 8 and newer SDKs. The frontend is the current Vite `react-ts` template (React 19, which satisfies "React 18 or newer").
- Backend tests start their own throw-away `postgres:16-alpine` container through Testcontainers, so `dotnet test backend` needs a running Docker daemon but no manual database or port; they exercise the real migrations and SQL, which an in-memory fake would not.
- Concurrency tests (`ConcurrencyTests`): all requests are created first and released through one gate so they are in flight together; student ids are fixed distinct 17-digit numbers so runs are reproducible and a `409` can only mean "class full". The two-instance test uses a second in-process host (`WebApplicationFactory.WithWebHostBuilder`) on the same database, with its own services, gate, pool and sweeper, so only the database is shared. Real separate OS processes were measured by hand but are not part of the automated suite, to keep `dotnet test backend` one command with Docker as the only prerequisite.
