# Assumptions

Decisions the specification left open, each with its reasoning.

## Identifiers

- Class ids are `c_` + 16 lower-case hex characters (64 random bits from a cryptographic RNG), e.g. `c_3f9a1b7c5d2e4a68`. Hold ids use the same scheme with prefix `h_`.
- Reason: opaque, non-guessable, non-sequential (no count leak), short enough to read out, and generated in the application so no database round trip or sequence is needed. Uniqueness is guaranteed by the primary key; a collision (about 1 in 10^19 per pair) would surface as a 500 rather than silent corruption.

## Error codes and responses

- Every error response is JSON `{ "error": "<machine_code>", "message": "<human sentence>" }`. This includes framework-produced errors (malformed JSON, unknown route, wrong method, unhandled exception → 500 `internal_error`) so the UI only has to parse one shape. The `message` never contains stack traces or internals.
- `POST /classes`: `400 validation_failed` when `name` is missing, blank (after trimming) or longer than 200 characters, or `totalSeats` is missing, `null` or below 1. `400 invalid_request` when the body is not valid JSON or a field has the wrong type (for example `"totalSeats": "many"` or `2.5`). Accepted names are stored trimmed.
- `GET /classes/{classId}`: `404 class_not_found` for an unknown id.
- Unknown route → `404 not_found`; wrong HTTP method → `405 method_not_allowed`.
- Student identity (`X-Student-Id`, required on `POST /classes/{id}/holds` and `GET /me/holds`): `400 student_id_required` when the header is absent or blank, `400 invalid_student_id` when it is not exactly 17 ASCII digits `0-9` (full-width or other-script digits are rejected). The header is checked before the class is looked up, so a bad header is a 400 even for an unknown class. The messages are written to be shown to a guardian as they are.
- `POST /classes/{classId}/holds`: `404 class_not_found`; `409 already_applied` when the student already has an active hold in that class; `409 no_seats_available` when the class is full. The duplicate check runs first, so a student who already holds the last seat is told they already applied rather than that the class is full.
- `GET /holds/{holdId}`: `404 hold_not_found`. It needs no header and returns exactly the contract fields (no `studentId`), so knowing a hold id does not reveal whose application it is.
- `GET /me/holds`: newest application first; an empty array when the student has none.
- `POST /holds/{holdId}/confirm` and `DELETE /holds/{holdId}` (both need `X-Student-Id`, validated first, then):
  - Unknown hold → `404 hold_not_found`. Another student's hold → `403 not_your_hold` (a 403 rather than a 404: hold ids are random and unguessable, and `GET /holds/{id}` already reveals existence, so hiding it would add nothing and the 403 gives the guardian a clear message). The hold is left untouched.
  - Confirm: `HELD` and unexpired → `200 { holdId, status: "CONFIRMED" }`. Already `CONFIRMED` → `200` again, nothing changes (idempotent, required by the spec). Expired (stored `EXPIRED`, or `HELD` past `expiresAt`) → `409 hold_expired`. `CANCELLED` → `409 hold_cancelled`. An expired hold is never revived; the guardian applies again.
  - Cancel policy: `HELD` and unexpired → `204`, status `CANCELLED`, the seat is free at once and the student may apply again. Already `CANCELLED` → `204` (idempotent: the requested end state already holds). `CONFIRMED` → `409 hold_confirmed`: once the fee is paid the application cannot be withdrawn through this API, because there is no refund flow and silently freeing a paid seat would be wrong. Expired → `409 hold_expired` (nothing to cancel; the status stays `EXPIRED` rather than becoming `CANCELLED`).
  - `409 hold_state_changed` exists only for the race where the hold changes between the conditional update and the follow-up read in a way the update should have caught; the client can simply retry.

## Configuration

- Database: the standard ASP.NET Core key `ConnectionStrings__Default` (Npgsql connection string). The app refuses to start without it. `appsettings.Development.json` points at the Postgres from `docker-compose.yml` on `localhost:5432` for `dotnet run` outside Docker.
- Schema is created and updated by EF Core migrations that run automatically at startup, so a fresh database needs no manual step.
- CORS allows any origin, header and method. There are no cookies or credentials (identity is a plain header), so a wildcard origin carries no extra risk and works for whatever host/port the frontend is served from.
- Time is read from an injected `TimeProvider` (UTC); timestamps are stored as `timestamptz`.

## Hold expiry mechanics

- Lifetime comes from the `HOLD_DURATION_SECONDS` environment variable (whole seconds, at least 1, default 600). An invalid value stops the app at startup instead of failing on the first request.
- `createdAt` is the request time truncated to whole seconds and `expiresAt = createdAt + HOLD_DURATION_SECONDS` exactly, so the serialized value (`2026-11-01T04:10:00Z`, UTC, whole seconds, trailing `Z`) matches the contract example and the stored value. A hold therefore lives up to one second less than the wall-clock time since the request.
- A hold is expired when `now >= expiresAt`. Every read computes the status: a stored `HELD` row past its `expiresAt` is reported `EXPIRED`, and it is not counted as held or as occupying a seat, whether or not any background job has rewritten the row yet.
- Only `CONFIRMED` and unexpired `HELD` holds are "active": they occupy a seat and block a second application by the same student to the same class. `EXPIRED` and `CANCELLED` holds do neither, so a student can apply again after expiry or cancellation.
- Sweeper: a background service in every backend instance rewrites stored `HELD` rows whose `expiresAt` has passed to `EXPIRED`, so the database itself is correct without any API call. It runs once at startup and then every `EXPIRY_SWEEP_INTERVAL_SECONDS` (whole seconds, at least 1, default 2, invalid values stop the app at startup). Reads do not depend on it: they compute `EXPIRED` and exclude lapsed holds from the seat counts, so a seat is released at `expiresAt` itself, not at the next sweep. The sweeper is what makes the stored status, `holds` rows and any direct database query agree, and it clears lapsed rows before a later step relies on stored status.
- A failed sweep (for example the database is briefly unreachable) is logged and retried on the next tick; it does not stop the API. The sweeper and the hold lifetime read time from the same injected `TimeProvider` (UTC).

## Concurrency strategy

- **Capacity (`heldSeats + confirmedSeats <= totalSeats`): pessimistic row lock on the class row, in PostgreSQL.** `POST /classes/{id}/holds` passes the gate and the plain-read refusal described below, then runs one transaction that starts with `SELECT total_seats FROM classes WHERE id = ? FOR UPDATE`. Then, still inside the transaction and holding the lock: read the clock, store every lapsed `HELD` hold of this class as `EXPIRED`, check for an active hold by the same student (409 `already_applied`), count the class's active holds (`CONFIRMED`, or `HELD` and unexpired) and refuse with 409 `no_seats_available` if the count has reached `totalSeats`, otherwise insert and commit.
  - Why it holds with any number of threads or backend processes: the lock lives in the database, not in the process. Applications for the same class queue on the row lock (applications for different classes do not block each other in the database, and the in-process gate keeps a busy class from holding up others, see below). Under READ COMMITTED each statement after the lock sees everything committed by the previous lock holder, so the count each one checks already includes every seat granted before it, and the transaction that inserts is the only one that can be counting at that moment. No in-process lock is what makes it correct, so a second backend instance on the same database (the SPEC 7.1 bonus) is covered by exactly the same mechanism.
  - Nothing else can add to the occupied count: the only `INSERT` into `holds` is that transaction. The other writers only move a row out of the active set (cancel: `HELD` to `CANCELLED`; sweeper and the application's own expiry step: `HELD` to `EXPIRED`) or convert one active row into another (confirm: `HELD` to `CONFIRMED`), none of which can push the total over capacity, and a lapsed hold is never revived (confirm requires `expires_at > now`). So none of them needs the class lock.
  - Backstop: a partial unique index `ux_holds_active_student_class` on `holds (class_id, student_id) WHERE status IN ('HELD','CONFIRMED')` (a migration) enforces SPEC 5.3 inside PostgreSQL even if some code path skipped the lock. A violation is caught and answered with the same `409 already_applied` as the explicit check. The index does not know about time, which is why the transaction first stores the class's lapsed `HELD` rows (including the student's own) as `EXPIRED`.
  - A partial index `ix_holds_held_expires_at` on `holds (expires_at) WHERE status = 'HELD'` serves the sweeper; the existing `(class_id, status, expires_at)` and `(student_id, created_at)` indexes serve seat counts and `/me/holds`.
  - Connection pool: every waiting application holds one connection while it queues on the lock, and Npgsql's default pool (100 per process) plus PostgreSQL's default `max_connections` (100) let two processes under a burst fail requests with "too many clients" (seen in a 2-process, 200-request test run, 86 of them 500s). The app therefore sets `Maximum Pool Size=30` unless the connection string sets its own; extra requests wait for a free connection. Three instances then fit in the default server limit. After the change, 2 processes with 1000 simultaneous requests for 500 seats gave exactly 500 `201`s and 500 `409`s, and both instances reported held 500, available 0.
  - Burst handling: each application that reaches the class lock keeps a pooled connection while it queues, and one class admits roughly 100 granted applications per second on the development machine, so a burst of thousands used to exhaust the pool and fail with `500` after Npgsql's 15 s pool timeout (a reviewer observed 3000 simultaneous requests for 500 seats giving 623 `500`s, 5000 for 2000 seats giving 3678). Now: (1) a gate (`ClassWriteGate`) is the FIRST thing an application passes, before any database access. It admits at most 3 applications per class and 15 per process at once (a fifth of the half-pool for one class, half the pool in total, so three instances still fit in PostgreSQL's default connection limit); the rest wait in memory (connections are handed out first come, first served, so without this a confirm or a page refresh would queue behind thousands of applications' first queries), and a request leaves the queue cleanly if its client disconnects. A request takes its class's slot first and a process-wide slot second, so a burst on one class waits on that class's slots without holding process-wide ones: an application to an idle class is not held up (a reviewer measured 26.7 s behind a 1200-request burst when the gate was one global semaphore; a test now requires a few seconds). The per-class gates are a fixed set of 64 chosen by hash of the class id, not one per id seen (ids come from the URL, so a dictionary would grow without bound); two classes that share a gate only share a queue. (2) Holding a slot, the application does a single plain read: unknown class (404), a student who already holds an active application (409 `already_applied`) or a class with no free seat (409 `no_seats_available`) is answered right there, without a transaction or the class lock. In a burst every request arrives before anyone has been granted anything, but by the time a queued request reaches the front the class is usually full, so the futile applications drain at read speed. That read can be slightly stale (a seat may just have been freed) and then a request racing a cancellation is told "full", as if it had arrived a moment earlier; it can never grant a seat, every grant goes through the locked path, which repeats all the checks. (3) The gate is a throughput guard only: correctness comes from the database lock, which also covers other processes. Measured with 2 backend processes on one Postgres (single global gate, before the per-class change): 3000 simultaneous requests for 300 seats gave 299 `201`s and 2701 `409`s in about 12-17 s; 4000 requests for 3000 seats gave 2999 and 1001 in about 70-80 s (all grants are serialized by the lock at roughly 40 per second); no 5xx in any run and both instances reported identical counts. So seat counts are always right, but a burst that really grants thousands of seats in one class takes a minute; a client with a shorter timeout would see its own timeout, not a server error.
  - Final measurement (per-class gate, 2 backend processes on one Postgres, probes sent with `curl` 2 s into the burst): 3000 requests for 300 seats gave 299 `201`s + 2701 `409`s in 12 s; 2500 requests for 2000 seats gave 1999 + 501 in 44 s (about 46 grants per second, serialized by the class lock). During those bursts a confirm answered in 9-69 ms, a class read in 8-47 ms and an application to another, idle class in 26-30 ms; no 5xx and both processes reported identical counts.
  - Limits of the "idle class is not held up" guarantee: it holds while an idle class has a free per-class slot and the process still has a free process-wide slot. Classes are hashed into 64 gates, so about 1 class in 64 shares its queue with another, and with 5 or more classes busy at the same moment (5 x 3 slots) the 15 process-wide slots are all in use, so a further class queues behind them. In practice the wait is short because granted and refused applications both finish in milliseconds (a reviewer's 8-hot-class run still answered an idle class in 0.14-0.19 s), but it is a throughput trade-off, not a hard guarantee.
  - If the database still cannot serve a request in time (pool timeout, lock/command timeout, server out of connections), the answer is `503 service_busy` with `Retry-After: 2` and a readable message, not a 500. A client that disconnects mid-request is dropped silently (logged status 499), not reported as a server error. Per-request noise is kept out of the logs under load: EF's per-command logging and the framework's stack trace for every handled 409/404 are switched off in `appsettings.json` (real 500s are still logged by the app's own handler).
- Confirm (`POST /holds/{id}/confirm`) is ONE conditional `UPDATE ... WHERE id = ? AND student_id = ? AND status = 'HELD' AND expires_at > now`, with no class lock and no gate. Confirming turns one active hold into another, so it cannot overbook by itself; the one subtle case is a hold that expires at the very moment its owner confirms. That race is closed by row locks: an application first marks every lapsed `HELD` row of the class `EXPIRED` with an UPDATE (before it counts), and an UPDATE has to take each row's lock. If the confirm already holds that row, the application's UPDATE waits for it, re-reads the row as `CONFIRMED`, skips it, and the count that follows includes it (the seat is not given away). If the application's UPDATE gets the row first, the confirm's UPDATE waits, re-reads `EXPIRED` and matches nothing (409). Either way both agree on whether the hold counts. A test pins this deterministically (a transaction holds the lapsed hold's row, the application must wait, the "confirm" commits, the application then counts the hold and answers 409). Because confirm does not need the class lock it is never queued behind applications: during a 3000-request burst on a 2-process setup, a `curl` confirm answered in 15 ms and a class read in 8 ms. (A first version had confirm take the class lock, sharing the applications' queue, to get the same ordering; a reviewer measured a confirm taking 20 s during a burst, so it was replaced by the row-lock argument above.) The row can only move out of `HELD` once, so repeated or simultaneous confirms cannot count a seat twice; a test fires 20 parallel confirms at one hold and expects `confirmedSeats` to be 1.
- Cancel (`DELETE /holds/{id}`) is likewise a single conditional `UPDATE ... WHERE id = ? AND student_id = ? AND status = 'HELD' AND expires_at > now` with no lock: it can only remove a hold from the active set, which can never overbook a class.
- Clock reads: an application reads the clock after it holds the class lock, never before, so a request that queued for seconds behind others does not stamp a stale `createdAt`/`expiresAt` or judge expiry with an old "now". Confirm and cancel read their own clock before their UPDATE; the row-lock argument above is what keeps that consistent with an application's later reading. All instances are assumed to have clocks that agree to well under a second (same host or NTP-synced hosts, as in `docker compose`); expiry decisions compare `expires_at` against the application's clock, not the database's.
- Expiry sweeper: every instance runs the same statement, `HoldExpiry.ExpireAllLapsedAsync`: it locks the lapsed `HELD` rows with `SELECT id ... ORDER BY id FOR UPDATE` and sets those rows to `EXPIRED`. It needs no leader election or class lock: the statement is idempotent, a row can move out of `HELD` only once, and confirm/cancel use the opposite predicate (`expires_at > now`), so a sweep racing a confirm leaves exactly one winner. Tests run two backend instances sweeping one database, and run sweeps against applications over the same lapsed rows (next bullet).
- Deadlocks between the two multi-row expiry statements: the sweeper (all classes) and an application's own-class expiry both update many rows at the same time. A plain `UPDATE ... WHERE` locks rows in whatever order its plan scans them (by student for one, by physical position for the other), so two such statements over overlapping rows can each hold what the other needs and PostgreSQL aborts one with `40P01 deadlock detected`. A reviewer reproduced this as 6 `500`s in 577 applications under churn (short holds, two processes), and a test reproduced the exact error. Both callers now lock the rows first in id order (`HoldExpiry`, shared by the sweeper and `CreateHold`), so they can never wait on each other in a cycle; `FOR UPDATE` still re-checks the predicate after waiting for a row, so a row a concurrent confirm turned `CONFIRMED` is skipped (which the confirm race argument above depends on). As a safety net `40P01` is also treated like the other "try again" database failures: `503 service_busy` with `Retry-After`, never a 500, and the sweeper simply retries on its next tick. A test runs a sweep against an application over a couple of hundred shuffled lapsed holds, 80 rounds at random relative offsets (with the old statements it fails on the first rounds with `40P01`). After the fix a 90 s two-process churn run (2 s holds, 1 s sweeper, 60 workers applying, confirming and cancelling) and a 60 s lapse-heavy run (80 workers, 5418 grants) gave no 5xx and no class above its capacity.
- Startup: every backend instance applies pending migrations at startup under a PostgreSQL advisory lock (`pg_advisory_lock`) taken on its own non-pooled connection to the always-present `postgres` maintenance database (advisory locks are per database, and the application's own database may not exist yet: EF still creates it, as before; if the maintenance database is not reachable with these credentials, the application's database is used). EF Core 8 does not lock while migrating, and two instances starting together on a fresh database (`backend` and `backend2` in `docker compose`) raced on creating `__EFMigrationsHistory`: one crashed with a duplicate-key error (seen in a manual two-process start). With the lock the second instance waits and then applies nothing. Tests start four instances at once on a fresh database, and start one against a server where the database does not exist.
- The migration that adds the unique index first repairs rows written before it existed, so it cannot fail startup on an old database: lapsed `HELD` rows become `EXPIRED`, and where one student still has several active holds in one class it keeps a `CONFIRMED` one (money was paid) or else the newest, and cancels the others. A test applies the first migration, inserts such rows, runs the rest and checks the result.

## Frontend shell and student identity

- Routing is hash based (`#/classes`, `#/classes/new`, `#/application`, `#/application/{holdId}`, `#/my-applications`), with no routing library and no server rewrite rules, so a refresh or a pasted link stays on the same screen behind any static file server.
- The "Application" screen needs a hold id, so its navigation entry opens a small form that takes the hold id the backend returned and goes to `#/application/{holdId}`; the Classes and My Applications screens link to it directly.
- The student id box saves exactly what is typed (trimmed) to `localStorage` key `admission.studentId`, valid or not, so a half-typed number is not lost on refresh; validity is `^[0-9]{17}$` (ASCII digits only, the same rule as the backend, full-width digits are flagged). Other tabs follow changes through the `storage` event. If storage is blocked the box still works in memory for that tab.
- An invalid id blocks student actions in two places: screens that need it render a message instead of their content (`StudentGate`), and the API client refuses to send any student-scoped call with an invalid id (it fails locally with code `invalid_student_id`), so no action can slip past a screen that forgot the gate.
- The API client turns every failure into `ApiError { code, message, status }`: the backend's `error` and `message` when the body has them, else `network_error` (fetch rejected), `server_error` / `request_failed` (non-JSON error body, with a generic message by status) or `invalid_response` (success status with an unreadable body).
- `VITE_API_BASE_URL` is read when the frontend is built or started (Vite inlines it); blank or unset means `http://localhost:8080`; trailing slashes are removed.
- Error boundaries: an outer one for the whole app and one around the current screen, so a screen that crashes keeps the ID box and navigation usable; navigating to another screen retries rendering. Errors thrown in event handlers or promises are not caught by React boundaries; those paths show their own error text through the API client's `{ code, message }`.

## Frontend: create class and class list

- Create Class checks the same rules as the backend before sending (name trimmed, 1-200 characters, no control characters; seats a whole number from 1 to 2,147,483,647 because the backend stores a 32-bit integer) and shows each message under its field. The backend's own 400 message is still shown if it rejects something the browser accepted. After success the form is cleared and stays on the screen (an admin often adds several classes) with a link to the list; after a failure the typed values are kept.
- Class List fetches `GET /classes` when opened. Applying does not poll yet (live refresh is a separate step, see Frontend polling interval); after a refused Apply the list is refetched, because a refusal usually means the counts on screen were stale. A failed refetch keeps the last good list on screen.
- Apply is disabled while the student id is invalid, while the class shows 0 available seats ("Full" next to it), and while another Apply is in flight (no double submit). The button's tooltip says why it is disabled. Seat counts on screen can be stale, so the server still decides: `409 no_seats_available` and `409 already_applied` messages from the backend are shown above the table as they are, and the user stays on the list. Success goes to `#/application/{holdId}`.
- Button label is "Apply (আবেদন করুন)" (English with the Bengali wording from the brief).

## Frontend: application detail and my applications

- The application screen (`#/application/{holdId}`) shows what `GET /holds/{id}` returns (no header needed, so anyone with the id can look at the status) plus the class name from `GET /classes/{classId}`; if that second call fails the class id is shown instead and the status is still usable. The Pay and Cancel buttons need the student id: with an invalid id they are disabled with a tooltip and a hint.
- Pay ("Pay admission fee (ভর্তি ফি দিন)") and Cancel ("Cancel (বাতিল)") are enabled only while the status shown is `HELD`, and only one action runs at a time. The page shows the new status from the response at once and refetches in the background to confirm it. Cancel asks once more inline ("Yes, cancel it" / "Keep it"), because it releases the seat and a mis-click should not do that.
- The server decides, the screen only mirrors it: a refused action (`hold_expired`, `not_your_hold`, `hold_confirmed`, ...) shows the backend's message and refetches the hold, so a stale `HELD` turns into `EXPIRED` right after the refusal. Until live expiry is built (separate step), a hold that lapsed while the page was open still shows `HELD` with the buttons enabled until the next fetch.
- `Expires at` is shown in the browser's local time and format (`toLocaleString`); the status text is the API value unchanged (`HELD`, `CONFIRMED`, `EXPIRED`, `CANCELLED`).
- My Applications is keyed by the student id: changing the id shows the loading state and then that student's list (an invalid id shows the "enter a valid ID" message and fetches nothing). It lists the backend's order (newest first), each row linking to the detail screen. Data is fetched when the screen opens; there is no polling yet.
- Loading and refetching go through one hook (`useLoad`): a failed background refetch keeps the data already on screen; an error on the first load offers "Try again".

## Repository and tooling

- Solution uses the classic `.sln` format (not `.slnx`) so it builds with both the .NET 8 and newer SDKs.
- Frontend scaffolded with the current Vite `react-ts` template (React 19, which satisfies "React 18 or newer").
- Backend integration tests start their own throw-away `postgres:16-alpine` container through Testcontainers, so running `dotnet test backend` needs a running Docker daemon but no manual database setup or port. The tests exercise the real migrations and real SQL; an in-memory fake would not catch Npgsql/EF translation problems.
- The API binds `http://0.0.0.0:8080` (all interfaces, so it is reachable from outside a container) only when no address is configured. `--urls`, `ASPNETCORE_URLS` or `ASPNETCORE_HTTP_PORTS` take precedence, so a second instance on another port is `ASPNETCORE_URLS=http://0.0.0.0:8081`.
- Class names are trimmed and must not contain control characters (PostgreSQL rejects NUL in text and the rest are never legitimate in a class name), so bad input gets a `400 validation_failed` instead of a database error.
- Concurrency tests (`ConcurrencyTests`): all requests are created first and released through one gate so they are in flight together; student ids are fixed distinct 17-digit numbers so runs are reproducible and a `409` can only mean "class full". The "two backend instances" test uses a second in-process host (`WebApplicationFactory.WithWebHostBuilder`) on the same database: it has its own services, gate, pool and sweeper, so only the database is shared. Real separate OS processes were measured by hand (see Concurrency strategy) but are not part of the automated suite, to keep `dotnet test backend` a single command with Docker as the only prerequisite.
