# AI Usage

## Summary

AI wrote most of the code, tests and documents in this repository; a human set the task, supplied the brief and decides what to submit. Every AI claim that mattered was checked by running something (tests, a real two-process run, a browser against a real backend, a clean `git clone` followed with only Docker), and the mistakes that this found are listed honestly below.

## Tools used

- **Claude (Anthropic)**, through a coding-agent command-line tool: design, implementation, tests, Docker files and documentation, working feature by feature with small commits.
- **A second AI agent session** was used after each feature as an adversarial reviewer: its only job was to find defects (it re-ran builds and tests, started the real stack, drove the UI in a headless browser, fired load bursts and races). Several of the problems listed below, such as the connection-pool exhaustion under bursts, the deadlock and the stale-clock race, were found this way and not by the tests I had written.
- Non-AI instruments for checking the AI's work: Testcontainers, Docker, `curl`, `netstat`, scripted headless Chromium.

## Where AI was used

- Repository skeleton, docker-compose, documents.
- Database schema (EF Core entities, migrations), class endpoints, uniform error handling.
- Seat holds, confirm, cancel, the expiry sweeper, the class-row lock transaction, the partial unique index, overload handling, and their Postgres-backed tests (including the concurrency suite: 200 requests for 10 seats, 50 parallel confirms, two backend instances on one database). Tests were also checked by temporarily breaking the code (removing `FOR UPDATE`, disabling the sweeper, disabling the gate, removing the migration lock) and confirming they then fail.
- Frontend: app shell and student-ID box, API client, the four screens, live countdown and polling, error banner and boundaries, all exercised in a browser against a real backend.
- Dockerfiles and the compose stack, checked with a clean `docker compose up --build`, a `down`/`up` data-survival check and a black-box API check.
- `README.md`, `ASSUMPTIONS.md` and this file.

## Where the AI was wrong, and how it was caught

**Backend and build**

- `dotnet new sln` on the .NET 10 SDK produced a `.slnx` file; caught while planning the Docker build on the .NET 8 SDK; replaced with a classic `.sln`.
- The seat-count query projected into a positional record and then filtered it; EF Core could not translate it and every class endpoint returned 500. Caught by the integration tests; fixed with an object initializer.
- Pinned `Microsoft.EntityFrameworkCore.Design` to 8.0.13 next to Npgsql 8.0.11, causing assembly conflicts (CS1705). Caught by the build; both are on 8.0.11.
- The default port was set with a `Urls` entry in `appsettings.json` and documented as overridable by `ASPNETCORE_URLS`; it is not (the JSON value won), which would have blocked a second instance on another port. Found by actually starting the API with `ASPNETCORE_URLS`; the default is now applied in `Program.cs` only when no address is configured.
- A class name containing NUL passed validation and made PostgreSQL return 500. Found by probing; control characters are now rejected with 400 and a test covers it.
- A `/me/holds` test reused one fixed student id that other tests had used in the shared database, and another asserted JSON property names in the wrong sort order (the API was right). Both caught by the failing tests.
- A local smoke run pointed at `localhost:5432` and got a password failure that looked like a credentials bug; two listeners were bound to that port. Caught with `netstat`.

**Concurrency and overload (the hard part)**

- The first class-row lock was correct (exact counts) but left Npgsql's default pool of 100 connections per process: two backend processes and 200 simultaneous requests gave 86 responses of 500 ("too many clients"). The in-process tests could not show it because they use one process; found by running two real processes against one database. Fixed by bounding the pool.
- Bounding the pool was not enough: stress bursts of 3000 and 5000 simultaneous applications gave 623 and 3678 responses of 500 (pool exhausted after 15 s queueing on the lock), although the counts stayed exact. Fixed with a per-process gate in front of the lock, a `503 service_busy` mapping for remaining timeouts and a 3000-request test (checked by disabling the gate). My earlier tests used only 1000 requests.
- A first "fast refusal" read ran before the gate, so in a burst it changed nothing and made the 3000-request test slower (13 s to 39 s); it now runs after a gate slot is taken. My single global gate let one hot class occupy every slot, so an application to an idle class waited 26.7 s; there is now a per-class slot plus a process-wide one, in a fixed set of 64 gates by hash (my first idea, a dictionary keyed by class id, would grow without bound).
- Further findings from stress tests: confirm judged expiry with an older clock reading than an application (a possible overbooking by one, not reproduced); an application read the clock before waiting for the lock (stale `createdAt`); the unique-index migration would crash start-up on an old database holding duplicates. Fixed with clock reads after the lock and a repairing migration (with a test). My first fix for the confirm race made confirm take the class lock, and a confirm then took 20 s during a burst; the final fix closes the race with row locks (applying marks the class's lapsed rows expired before counting) and keeps confirm a single `UPDATE`, with a deterministic test (checked by reverting the fix).
- Two backend processes started at the same moment on an empty database crashed one of them (EF Core 8 does not lock migrations). Found by accident, not by a test; fixed with an advisory lock and a test that starts four instances at once. My first lock took a pooled connection and made a `Maximum Pool Size=1` test host hang; a later check found it no longer created a missing database. It now uses its own connection to the `postgres` database, with a test.
- The class-wide "expire every lapsed hold" `UPDATE` I added for the confirm race deadlocked with the sweeper's multi-row `UPDATE` under churn (PostgreSQL `40P01`; 6 of 577 applications got a 500). I had reasoned only about confirm versus apply, not about two multi-row statements locking rows in different orders. Fixed by locking rows in id order in one shared helper and mapping `40P01` to 503. My first regression test passed even against the old code (the sweep finished before the application reached its `UPDATE`); I rewrote it to start the sweep at random few-millisecond offsets, and it now fails against the old statements.
- While measuring confirm latency during a burst I read 10 to 78 s from a Node `fetch` probe and nearly redesigned the server; a plain `GET` showed the same delay, which pointed at the load generator (the same requests from `curl` took 8 and 15 ms).

**Frontend**

- The first error boundary wrapped the whole app, so a crashing screen took the ID box and navigation with it. Caught by making a screen throw and looking at the page; a second boundary now wraps the current screen.
- `createClass` was typed as returning the full class summary, but `POST /classes` returns only `id`, `name`, `totalSeats`. Caught re-reading the contract before anything used the missing fields.
- The first `useLoad` hook had two identical functions, and `mutate` could be overwritten by an older request still in flight (a status just set from the Pay response replaced by a stale `HELD`); a failed refetch also replaced data on screen with an error. Found by re-reading the ordering before testing.
- The first polling design restarted the request effect on every tick, so on a slow server no answer would ever arrive; it now skips a tick while a request is in flight or the tab is hidden. I also first treated "the browser clock says expired" as final, which on a browser whose clock is ahead disables Pay on a hold the server still honours; a fetch sent after `expiresAt` that still says `HELD` now overrules the clock (tested with a browser clock 10 s ahead).
- The student-ID box flagged the number as invalid from the first keystroke, each screen rendered its own error markup, a hung request stalled polling, a missing hold was refetched every 15 s, and the class-name request on the application screen failed silently and never retried. All found by browser runs against the real backend (including blocking single requests); fixed with a "still typing" state, one `ErrorBanner`, a 15 s request timeout, no timer retry of 4xx answers, and a visible notice plus retry for the class name.
- Several of my own test scripts were wrong, not the product: navigating to the same hash does not reload a page, a sampling loop stopped before the confirming refetch, and a "backend down" check stopped the backend before the page loaded so it tested the first-load error. Each was caught because the result contradicted the code, and re-run correctly.
- The frontend tests (Vitest, React Testing Library) all passed the first time they ran, which proves little, so I broke the code on purpose and re-ran them: expiring a minute late, letting a full class keep an enabled Apply button, and not writing the student id to `localStorage` each made the matching tests fail, then I reverted each change. That exercise still missed something: the tests of "the student id persists" called the storage function directly, and nobody had tested the box a user actually types into, so unwiring its `onChange` left every test green; an independent mutation run found it, and `StudentIdBar` now has its own tests (typing saves, clearing removes, still-typing, flagging, another tab). The same run also showed that my README gave a Node version (20.19+) older than what Vitest 5 and jsdom 29 need; it now says 22.13+. When I re-ran my own mutation check, two of my "revert" edits were rejected because I had sent them with stale file tags, leaving the mutations in place; I noticed from the failing tests, reverted them with fresh tags and confirmed with `git diff` that the source files were unchanged. The tests replace only the API layer (the real error classes, hooks, timers and components run), use fake timers for the countdown, and one test sends a real `409` body through the real client; the "student id survives a reload" test re-imports the module after `vi.resetModules()` to simulate a reload, the one place a dynamic import is intended.

**Docker and documentation**

- The compose file published PostgreSQL on host port 5432, where a local PostgreSQL already listens (caught with `netstat` before it failed), so the database is not published. The default project name would also have reused an unrelated volume named `prototype_pgdata`, which `docker compose down -v` deletes; the compose file now has a fixed project name.
- The first full image build failed in `dotnet restore` (`NU1301`) because the machine's internet connection dropped for a few minutes; an environment problem, and the same Dockerfile built once it was back.
- Misplaced line-range edits (in the compose healthcheck, the README and two screens) left duplicate or missing lines; each was caught by reading the file back, the build or the linter before anything ran.
- The first README showed the Windows `cmd` fast-expiry command as `set HOLD_DURATION_SECONDS=20 && …`, which stores the value `20 ` with a trailing space and fails validation; changed to `set "HOLD_DURATION_SECONDS=20" && …` while proofreading.
- After writing the README I followed it literally on a fresh `git clone` using only Docker: all three services came up healthy, `http://localhost:8080/classes` answered and the frontend returned 200.
- Second backend: my first README example for the two-instance check was a pseudo-command ("a script that posts to both ports") and then a shell one-liner built on `xargs`/`sh` that I could not run in the shell I had; I replaced both with three `curl` commands that I ran against the stack (apply through one port, get `409` through the other, read the counts), and the larger burst figures come from runs I actually did against the stack.
- Second backend: mid-check, `localhost` ports 8080, 8081 and 3000 suddenly stopped answering (connection reset) while `127.0.0.1` and the containers were healthy. I first suspected my compose change; the cause was Windows' `wslrelay.exe` holding `[::1]` on those ports with a dead relay (an environment fault, not the compose file). It cleared after that one process was stopped with the user's permission, and the stack then passed the same checks through `localhost`.
