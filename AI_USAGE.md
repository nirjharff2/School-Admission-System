# AI Usage

## Tools used

- Claude Code (Anthropic) — scaffolding, implementation and tests, driven feature by feature.

## Where AI was used

- Repository skeleton: backend/frontend scaffolds, docker-compose, docs skeletons.
- Database schema (EF Core entities, migration), class endpoints, uniform error handling, and the Postgres-backed integration tests (Testcontainers).
- Seat holds: student-id validation, `HOLD_DURATION_SECONDS` handling, `POST /classes/{id}/holds`, `GET /holds/{id}`, `GET /me/holds` and their tests.
- Confirm and cancel: `POST /holds/{id}/confirm`, `DELETE /holds/{id}` (single conditional UPDATE each), the cancel-after-confirm policy and their tests, including a 20-way parallel confirm.
- Expiry sweeper: the `BackgroundService`, its interval setting and tests (real 1-second holds and sweeper on a separate database, two instances on one database); the sweeper tests were also checked by temporarily disabling the service and confirming they fail.
- Capacity invariant: the class-row lock transaction in `POST /classes/{id}/holds`, the partial unique index migration and its 409 mapping, the connection-pool bound and the tests; the lock test was checked by temporarily removing `FOR UPDATE` and confirming the burst test then fails.

## Where the AI was wrong, and how it was caught

- Skeleton: `dotnet new sln` on the .NET 10 SDK produced a `.slnx` file by default; caught while planning Docker builds on the .NET 8 SDK and replaced with a classic `.sln`.
- Class endpoints: the first seat-count query projected into a positional record and then filtered with `FirstOrDefaultAsync(r => r.Id == id)`; EF Core could not translate it and every class endpoint returned 500. Caught by the integration tests; fixed by projecting with an object initializer.
- Class endpoints: pinned `Microsoft.EntityFrameworkCore.Design` to 8.0.13 next to Npgsql provider 8.0.11, which produced EF assembly version conflicts (CS1705) in the test project. Caught by the build; aligned both on 8.0.11.
- Local smoke run: the AI first pointed the API at `localhost:5432` and got a password failure that looked like a credentials bug. Two listeners were bound to that port (the compose Postgres and another local server), so the connection reached the wrong one. Caught with `netstat`; the smoke run used a Postgres on another port instead.
- Port 8080: the AI set the default with a `Urls` entry in `appsettings.json` and documented that `ASPNETCORE_URLS` overrides it. It does not (the JSON value won), which would have blocked running a second instance on another port. Caught by the reviewing pass that actually started the API with `ASPNETCORE_URLS`; fixed by applying the default in `Program.cs` only when no address is configured.
- Class endpoints: a class name containing a NUL character passed validation and hit PostgreSQL, returning 500. Found by the same review; control characters are now rejected with 400 and covered by a test.
- Hold endpoints: the first `GET /me/holds` test reused one fixed student id that other tests had already applied with in the shared test database, so it saw foreign holds. Caught by the failing test; it now uses a fresh random id, and the other tests that count rows use their own classes.
- Hold endpoints: the same test asserted JSON property names in the wrong sort order (`className` before `classId` under ordinal ordering). The API output was right, the test was wrong; caught by the failing assertion.
- Capacity lock: the first version of the class-row lock was correct (counts were exact) but left Npgsql's default pool of 100 connections per process. In a manual run with two backend processes and 200 simultaneous applications, 86 requests returned 500 (PostgreSQL: "too many clients already"); with 300 requests 184 did. The in-process tests could not show it because they use one process. Caught by running two real processes against one database; fixed by bounding the pool (`Maximum Pool Size=30` by default) and re-running the burst (no 500s, exact seat counts).
- Capacity lock, review round: bounding the pool to 30 was not enough. The reviewer ran bursts of 3000 and 5000 simultaneous applications against two processes and got 623 and 3678 responses of 500 (connection pool exhausted after 15 s of queueing on the class lock), although the seat counts stayed exact. Fixed with a per-process gate in front of the lock transaction, a 503 `service_busy` mapping for any remaining timeout, and a test with a 3000-request burst (checked by disabling the gate: the test fails). My own earlier tests only used 1000 requests and never hit the 15 s limit.
- Capacity lock, review round: the same review found that confirm decided expiry with an older clock reading than an application did (a possible overbooking by one, not reproduced), that an application read the clock before waiting for the lock (stale `createdAt` under bursts), and that the new unique-index migration would crash startup on an old database holding duplicate active rows. Fixed: applications read the clock after the lock; the migration repairs such rows first and a test covers it. My first fix for the confirm race made confirm take the class lock and queue with the applications; the next review measured 20 s for a confirm during a burst. The final fix closes the race with row locks instead (applying marks the class's lapsed `HELD` rows `EXPIRED` before counting, which must wait for a concurrent confirm's row lock), keeps confirm a single UPDATE, and has a deterministic test (checked by reverting to the per-student expiry: the test fails).
- Startup race: starting two backend processes at the same moment on an empty database crashed one of them (EF Core 8 does not lock migrations; duplicate key on `__EFMigrationsHistory`). Found by accident while launching the two-process smoke run in parallel, not by a test; fixed with a PostgreSQL advisory lock around the startup migration and a test that starts four instances at once (checked by removing the lock: the test fails). My first version of that lock took a pooled connection, which made a `Maximum Pool Size=1` test host hang at startup; the 503 test caught it and the lock now uses its own non-pooled connection. The review then found it no longer created a missing database (the lock connection opened the target database first); the lock now uses the `postgres` maintenance database and a test starts an instance against a database that does not exist.
- Burst latency measurement: while checking confirm latency during a 3000-request burst I first read 10 to 78 s from a Node `fetch` probe and nearly redesigned the server around it. Even a plain `GET /classes/{id}` showed the same delay, which pointed at the load generator, not the API; the same requests from `curl` took 8 ms and 15 ms. I kept the redesign only where a test or the reviewer showed a real server-side cause.
- Burst drain: my first "fast refusal" read ran before the gate; in a burst every request passes it before anyone is granted a seat, so it changed nothing and the 3000-request test got slower, not faster (13 s to 39 s). It now runs after the gate slot is taken, where the class is already full for most queued requests.
- Deadlock: the class-wide "expire every lapsed hold" UPDATE I added so that applying serializes with a racing confirm deadlocked (PostgreSQL 40P01) with the sweeper's multi-row UPDATE under churn, returning 500 to applicants (6 of 577 in the reviewer's two-process stress). I had reasoned only about the row-lock interplay between confirm and apply and not about two multi-row statements locking rows in different orders, and none of my tests overlapped the two statements. Found by the third review's stress run. Fixed by locking the rows first in id order in one shared helper (`HoldExpiry`) used by both, and mapping 40P01 to 503 as a safety net. My first regression test for it started the sweeps and the applications together; it passed even against the old statements (the sweep finished before the application reached its UPDATE), so I rewrote it to start the sweep at random few-millisecond offsets; it now fails on the first rounds with the old statements (checked) and passes with the fix. Two-process stress runs of 90 s and 60 s then gave no 5xx.
- Gate: my single per-process gate let one hot class hold all 15 slots, so an application to an idle class waited 26.7 s (reviewer). Now a per-class slot is taken first and a process-wide slot second, with the per-class gates in a fixed set of 64 chosen by hash (my first idea, a dictionary keyed by class id, would have grown without bound with ids from the URL). Measured with `curl`: an application to an idle class answers in about 30 ms during a 3000-request burst.
